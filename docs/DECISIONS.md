本文记录能够由当前实现、配置、工作流、仓库历史证明或由维护者明确确认的决策，不补写不存在的讨论。新决策应追加，不应静默改写既有记录。

## 记录格式

```markdown
## DNNN：决策标题

- 日期：YYYY-MM-DD 或“项目初始化阶段”
- 状态：有效 / 已取代 / 待定
- 背景：需要解决的问题和已知约束。
- 决策：实际采用的方案。
```

## D001：使用 Python 完成采集与静态构建

- 日期：项目初始化阶段
- 状态：有效
- 背景：项目需要定时抓取官方网页、解析 HTML、执行规则并生成公开产物。
- 决策：使用 Python 作为采集和构建语言，主入口为 `python -m src.finpolicy.radar`。
- 原因：当前实现统一使用 `requests`、BeautifulSoup、PyYAML、Jinja2 和 python-dateutil 完成流程。
- 后果或限制：运行环境必须安装 `requirements.txt` 中的 Python 依赖；当前没有浏览器渲染能力。

## D002：使用 JSON 持久化政策和运行状态

- 日期：项目初始化阶段
- 状态：有效
- 背景：MVP 需要保存历史政策，但目标是保持零数据库和低运维成本。
- 决策：使用 `data/policies.json` 保存政策，使用 `data/status.json` 保存最近一次来源状态。
- 原因：当前规模可直接读取、合并并由 Git 管理，无需数据库服务。
- 后果或限制：缺少数据库查询、事务、迁移和并发写入能力；数据量增长后读写整个文件的成本会上升。

## D003：第一版使用规则分析，不强依赖大模型

- 日期：项目初始化阶段
- 状态：有效
- 背景：项目需要相关性、分类、文件类型、摘要、重要性和影响提示，同时控制成本和不确定性。
- 决策：相关性与分类使用 YAML 关键词规则，摘要和影响使用确定性文本规则与模板。
- 原因：实现可本地运行，不需要 API Key，也不会把模型生成结果冒充官方内容。
- 后果或限制：规则可能误判、漏判，摘要质量受正文提取和句子规则限制；当前没有语义推理。

## D004：官方原文 URL 是政策记录的强制字段

- 日期：项目初始化阶段
- 状态：有效
- 背景：聚合页面必须让用户回到权威来源核对政策全文。
- 决策：每条政策保存 `url`，页面标题和“查看官方原文”均链接该 URL；合并时也使用规范化 URL 去重。
- 原因：项目输出包含自动规则摘要和影响提示，官方来源可追溯是准确性保障。
- 后果或限制：无法获得真实官方 URL 的记录不能作为有效政策；来源改链可能导致历史链接失效。

## D005：来源和单篇文章失败相互隔离

- 日期：项目初始化阶段
- 状态：有效
- 背景：不同政府网站可能独立改版、限流或临时不可用。
- 决策：每个来源有独立的异常边界，单篇文章处理也单独捕获异常；失败信息写入来源状态，流程继续处理后续来源。
- 原因：单点故障不应阻断整个政策站更新。
- 后果或限制：一次构建可能在部分来源失败时仍成功部署；维护者必须查看状态面板判断完整性。`status.json` 和失败隔离只能降低影响，不能解决官方站点对 GitHub Actions 运行器的长期可访问性风险，后续仍需监控。

## D006：使用配置驱动的通用 HTML 采集器

- 日期：项目初始化阶段
- 状态：有效
- 背景：MVP 需要以较少代码覆盖多个官方来源。
- 决策：在 `config/sources.yaml` 配置入口、允许域名和 URL 规则，统一由 BeautifulSoup 发现链接并解析详情页。
- 原因：对服务端渲染、结构相近的网站易于扩展，通常可通过配置调整路径。
- 后果或限制：JavaScript 驱动、验证码、API-only 和结构特殊的来源无法可靠处理，需要专用采集器。

## D007：拒绝未解析模板表达式和历史污染记录

- 日期：2026-08-06
- 状态：有效
- 背景：NFRA 原始 Angular 模板中的 `{{x.docSubtitle}}`、`{{data.publishDate}}` 等表达式曾被误收录为政策内容。
- 决策：候选和详情处理阶段检查模板表达式；详情真实 `<h1>` 可替代列表模板标题；最终标题、正文或 URL 仍含模板时跳过；合并阶段清理已持久化污染。
- 原因：无法可靠解析时跳过，比发布虚假政策字段更符合准确性目标。
- 后果或限制：检测规则不是完整模板语言解析器；新增表达式形式需要新增回归测试。当前主动跳过没有单条持久化失败记录，详细逐条失败审计暂不属于 MVP 必做项。

## D008：使用 Jinja2 生成静态网站并由浏览器端筛选

- 日期：项目初始化阶段
- 状态：有效
- 背景：项目需要公开展示政策，但不希望维护应用服务器。
- 决策：将完整政策列表渲染为 `public/index.html`，同时生成 JSON 和 RSS；`public/assets/app.js` 在浏览器中完成筛选。
- 原因：静态产物部署简单、成本低，不依赖在线后端。
- 后果或限制：每次更新需要重新生成和部署全部页面；数据量变大后首页体积和浏览器筛选成本会上升。

## D009：使用 GitHub Actions 定时运行并用 GitHub Pages 部署

- 日期：项目初始化阶段
- 状态：有效
- 背景：政策站需要无人值守地定期更新并公开访问。
- 决策：工作流每小时第 17 分钟运行，也支持手动和 `main` push 触发；构建完成后上传 `public/` 并部署到 <https://dontbetoolate.github.io/finpolicy-radar/>，当前不使用自定义域名。
- 原因：利用仓库现有托管能力实现低运维自动化。
- 后果或限制：受 GitHub Actions 调度、网络出口和 Pages 可用性影响；定时任务不保证严格准点。

## D010：自动工作流提交 `data/` 与 `public/` 到 `main`

- 日期：项目初始化阶段
- 状态：有效
- 背景：下一次抓取需要历史政策输入，仓库也需要保存当前静态发布产物。
- 决策：MVP 阶段继续提交 `data/` 和 `public/`。工作流在抓取后暂存这两个目录，有变化时由 `github-actions[bot]` 提交，并在 rebase 后推送 `main`。
- 原因：`data/` 保存政策历史，`public/` 支持当前 GitHub Pages 自动化流程；在零数据库架构下，Git 仓库承担现阶段的数据和构建产物持久化。
- 后果或限制：`main` 会产生定时机器人提交，生成时间和状态容易形成噪声；并发更新需要依赖 rebase 和工作流并发控制。数据量扩大后再评估独立数据分支、GitHub Release、对象存储或数据库，当前未选定迁移方案。

## D011：Git 写操作需要维护者明确授权

- 日期：2026-08-06
- 状态：有效
- 背景：个人开发者与 AI 助手协作时，commit、push、合并和发布会改变共享仓库或线上状态。
- 决策：默认允许在当前任务分支修改和测试，但不自动 commit、push、merge 或发布；每一步外部写操作都等待维护者明确指令。
- 原因：让维护者保留对历史和上线时点的最终控制。
- 后果或限制：任务交付通常分为修改、审核、提交、推送、PR 和部署多个明确步骤。

## D012：暂不在 MVP 文档任务中解决授权冲突

- 日期：2026-08-06
- 状态：有效
- 背景：当前阶段暂不正式开源，但仓库根目录包含 MIT `LICENSE`，README 同时包含限制复制、商业使用和二次发布的声明。
- 决策：保留现有 `LICENSE` 和 README，不在本次文档分支中删除或修改；另建独立任务确定最终开源与授权策略。
- 原因：授权选择需要维护者单独确认，不应作为项目上下文整理的附带改动处理。
- 后果或限制：冲突解决前，对外授权信息存在歧义；项目文档必须明确这是待处理问题，不能声称已经统一。

## D013：逐条跳过失败审计推迟到 MVP 之后评估

## D014：将 Pages 部署与政策更新工作流分离

- 日期：2026-08-10
- 状态：有效
- 背景：更新工作流在同一次运行中提交 `data/` 和 `public/` 后再部署 Pages。部署使用运行开始时的提交版本，而 `main` 已被机器人推进；同时，纯文档修改也会触发采集和部署。2026-08-06 的多次 Pages 部署在 artifact 上传成功后等待至 10 分钟上限并超时。
- 决策：`Update FinPolicy Radar` 只负责抓取、构建并提交生成文件；成功完成后，`Deploy FinPolicy Radar Pages` 从最新 `main` 的 `public/` 单独上传和部署。纯文档与授权说明文件不触发更新工作流。
- 原因：部署应以已提交的最新静态产物为准，避免生成提交与部署版本错位；文档变更不需要采集或发布网站。
- 后果或限制：一次成功更新会显示为两个 Actions 运行；Pages 服务本身临时不可用仍可能导致部署失败，需通过单独部署日志排查，不能视为已完全消除。

## D015：为 JavaScript 驱动来源使用公开 API 专用采集器

- 日期：2026-08-11
- 状态：有效
- 背景：国家金融监督管理总局列表页返回 Angular 模板，曾产生 `{{x.docSubtitle}}` 等污染记录；国务院政策文件库入口只返回 Vue 应用壳。通用 HTML 采集器无法可靠发现这两个来源的真实政策。
- 决策：总局通过其公开 `DocInfo` 列表和详情 API 获取真实 `docId`、标题、日期与正文，并构造可访问的官方详情页 URL；主域名接口被运行环境拒绝时，依次尝试内容等价的总局官方 Big5 镜像。中国政府网通过国务院政策文件库公开检索 API 发现真实官方 URL，只保留含金融语境词的候选，再用现有 HTML 详情解析。采集器仍执行域名、路径和模板表达式校验。
- 原因：无需浏览器渲染即可取得官方公开数据，同时继续满足真实官方 URL、字段可验证和单来源失败隔离要求。
- 后果或限制：公开接口路径和字段并非本项目控制，网站改版后可能需要同步调整；GitHub Actions 出口 IP 仍可能遇到 403，必须依赖来源状态和回归测试持续监控。

## D016：先判断政策材料资格，再计算相关性和重要性

- 日期：2026-08-11
- 状态：有效
- 背景：通用正文回退曾选中人民银行整页导航，导航中的“支付、征信、反洗钱”等词使一条单项清算行授权公告被误判为五星政策；会议、会见和统计信息也可能因金融科技关键词进入结果。
- 决策：正文提取按专用选择器优先级处理，并拒绝高链接密度和多导航标记的内容块；政策材料信号必须出现在标题中，同时排除会议新闻、署名文章、单项授权等一次性信息，然后才计算金融科技相关性、分类和重要性。摘要先移除重复标题、来源日期与打印纠错控件。五星仅用于高相关正式制度文件，监管动态最高 2 星、政策解读最高 3 星。
- 原因：关键词只能判断主题相关，不能证明页面属于政策文件；正文质量和材料类型必须成为相关性与评分的前置条件。
- 后果或限制：严格过滤会减少收录数量，并可能漏掉标题和正文均缺少常见政策用语的特殊文件；同一来源、同一标题的多个官方 URL 只保留最新发现的一条，不同来源的同名发布仍保留；新增页面形态需要通过来源级样本继续校准。

## D017：首版使用客观筛选与三级关注级别

- 日期：2026-08-12
- 背景：关键词分类容易让同一文件同时命中多个主题，1—5 星也难以向用户解释；现有样本更适合按官方来源、适用对象、发布形式和日期查找。
- 决策：首页筛选采用搜索、来源、适用对象、文件类型、发布日期范围和关注级别；主题分类继续保留在兼容数据中但不在页面展示。适用对象只根据标题和正文开头明确指向判断，无法可靠判断时使用“未明确”。文件类型优先使用官方栏目和标题发布形式，不扫描全文引用词。关注级别使用“核心关注、重点跟踪、一般参考”三级，并在页面公开筛选标准；底层 `importance` 兼容保存为 5、3、1。
- 原因：客观属性更便于稳定筛选，三级关注仍保留雷达产品的阅读优先判断，同时避免五星造成的假精确。
- 后果或限制：历史记录只保存摘要，适用对象可能暂为“未明确”；关注级别仍是规则判断，不代表发布机构评价，需要通过真实样本持续校准。

## D018：总局使用现行三个政策栏目并在列表阶段聚焦金融科技

- 日期：2026-08-12
- 背景：总局旧栏目 `926` 仅返回少量历史记录，漏掉 2026 年《银行业保险业人工智能安全开发应用的指导意见》。现行政策区实际由规章 `4214`、行政规范性文件 `4215` 和其他文件 `4216` 组成。
- 决策：总局采集器分页读取三个现行官方栏目，按真实 `docId` 去重，并在列表标题阶段保留直接涉及人工智能、数据、网络安全、信息科技、数字化、支付清算等金融科技核心领域的候选；继续使用官方详情 API 获取正文和简体官方详情页作为原文链接。
- 原因：完整扫描三个栏目可以避免单栏目漏采，标题阶段聚焦可防止每小时重复请求数百篇明显不相关的金融业务政策，并降低官方接口 403 或超时风险。
- 后果或限制：标题没有任何金融科技信号但正文相关的特殊文件仍可能漏掉；需通过已知重要政策回归测试和来源状态持续审计。
